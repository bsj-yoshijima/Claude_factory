# サーバ — ローカルで動かす

各ユーザーが自分の工場を持ち、WP・製造・売上・図鑑をサーバ（Postgres）で管理する。
これが唯一の構成で、旧・単一ユーザー版（`server.mjs` / `otel.mjs` / `/metrics`）は撤去した。

## 起動

```bash
npm install && npm run db:up && npm run dev
```

`db:up` は Postgres を起動したあと `db:migrate` まで流す。**スキーマを DB に当てるのは
`npm run db:migrate` だけ**で、サーバの起動処理は DB を書き換えない（後述）。

→ http://localhost:4321 を開く。`GOOGLE_CLIENT_ID` が未設定のあいだは **dev ログイン**
（メールアドレスを入れるだけ）が有効。ログインすると `/setup` に飛び、
`~/.claude/settings.json` に貼るブロックが出る。

4321 が埋まっている場合は `PORT=4400 PUBLIC_URL=http://localhost:4400 npm run dev`。

| コマンド | 内容 |
|---|---|
| `npm run dev` | サーバ |
| `npm run db:up` | **手元の docker** を起動してスキーマを当てる（`.env` の共有DBは触らない） |
| `npm run db:migrate` | **`.env` の向き先**にスキーマを当てる。共有DBではオーナーだけが実行する |
| `npm run db:migrate:local` | 手元の docker にだけ当てる（`db:up` / `db:reset` が内部で使う） |
| `npm run db:psql` | **手元の docker** の DB に入る（共有DBを見るなら `psql "$DATABASE_URL"`） |
| `npm run db:reset` | 手元の docker を作り直す（データも消える。migrate まで流す） |
| `npm test` | レシピ・製造機・サーバの全テスト |

`db:up` / `db:reset` / `db:migrate:local` は必ず手元の docker を対象にする。
共有DBを指す `.env` を持っている人が「手元を立ち上げるつもりで共有DBに DDL を流す」のを
防ぐため、`--local` が渡されたときは `DATABASE_URL` を捨ててから DB に繋いでいる。

### スキーマの世代管理

複数人が 1 つの DB を共有する場合、サーバ起動のたびに DDL と `wp_weights` の
上書きが走ると事故になる（`git pull` し忘れた人が 1 人起動しただけで、古い重みが
全員ぶんを上書きする）。そのため **DB を書き換える操作は `db:migrate` に集約し、
サーバは起動時にバージョンを読むだけ**にしてある。

| 役割 | やること |
|---|---|
| オーナー（スキーマ変更時） | `db/version.mjs` の `SCHEMA_VERSION` を上げてコミット → `npm run db:migrate` |
| メンバー（日常） | `git pull && npm run dev` だけ |

チームで 1 つの DB を共有する手順は [phase1-setup.md](phase1-setup.md) にまとめてある。

サーバは `db/version.mjs` と `schema_meta.version` を比べ、**DB が古ければ起動を止める**
（「オーナーの migrate 待ち」だとメンバーに分かるようにするため）。逆に **コードが古い
場合は警告だけ出して起動する**（スキーマの追加は基本 additive なので古いコードでも動く）。

## 実際に Claude Code を繋ぐ

`/setup` に出る JSON を `~/.claude/settings.json` にマージして、**新しい claude セッションを起動**する
（起動中のセッションには反映されない）。中身は2つ:

- `env` … OTLP の送り先とトークン。WP とスコアカードはここから来る
- `hooks` … `SessionStart` / `UserPromptSubmit` / `Stop` / `SessionEnd`。工場のキャラの在/不在

`PreToolUse` / `PostToolUse` は**意図的に使っていない**。実測でこの2つは 76回/時 走り、
いま 1ms で終わっているため、ネットワーク呼び出しを足すと 20〜50倍になって体感される。
使う4つは合計 約12回/時（5分に1回）で、既に 63〜138ms かかっているので差分は埋もれる。

## 構成

```
ブラウザ ──▶ server/index.mjs ──▶ Postgres
                  ▲   ▲
   OTLP/JSON ─────┘   └───── hooks
   (WP・スコアカード)        (エージェントの在/不在・プロジェクト名)
```

| ファイル | 役割 |
|---|---|
| `server/index.mjs` | HTTP。OTLP 受信 / hooks 受信 / API / 静的配信 / ログイン画面 |
| `server/game-data.mjs` | マスタの窓口。定義の正は `game/data/*.mjs`（クライアントと同じものを import する） |
| `server/ingest-otel.mjs` | OTLP → 分バケット。親子判定・重複排除 |
| `server/ingest-hooks.mjs` | hooks → `agent_sessions`。在/不在の減衰ルール |
| `server/wp.mjs` | 重みの定義と WP の集計 |
| `server/time.mjs` | JST の暦日。集計の境界を決めるので定義は1箇所だけ |
| `server/craft.mjs` | 製造エンジン（サーバ権威） |
| `server/api.mjs` | ゲーム API。💰・図鑑（`collection`）・在庫を書き換えるのはここだけ |
| `server/auth.mjs` | Google SSO / dev ログイン / 取り込みトークン |
| `server/db.mjs` | 接続プールとトランザクション。**スキーマは流さない**（`tools/migrate.mjs` の仕事） |
| `server/names.mjs` | 表示名と工場の既定名。ここだけが「◯◯の工場」を組み立てる |
| `db/schema.sql` | スキーマ。全部冪等。流すのは `npm run db:migrate` だけで、サーバの起動時には流さない |

## 設計上の要点

### 1. WP は「重みをかける前のカウント」で持つ

旧実装は生の OTLP ペイロードを全部ファイルに残し、起動のたびに全リプレイしていた。
実測すると **24MB/日/人**（20人 × 1ヶ月で 10GB）で、チーム展開すると破綻する。

代わりに `wp_source_minute (user_id, minute_ts, tool_name, is_subagent, ok_count)` と
`wp_metric_minute` に畳んで持つ。重みは `wp_weights` テーブルにあり、`wp_minute` ビューが
掛け算と1分上限を適用する。

- **重みを UPDATE するだけで全期間が再集計される**（wp.md §6 の性質をそのまま維持）
- サイズは **数KB/日/人**。3桁減る
- 旧実装の「ツールイベント20万件でサイレント打ち切り」が構造的に消える

生ペイロードはデバッグ用に短期間だけオブジェクトストレージへ置く想定だったが、**PoC では不要と判断した**（2026-08）。取り込みの解釈を間違えたときに遡って直せなくなる点だけ承知しておく → [scale.md](scale.md)

### 2. 製造をサーバへ移した

旧実装はブラウザの `tickCraft()` が製品を作って 💰 を足していたので、DevTools から
書き換え放題だった。リーダーボードを置く以上サーバに移す必要がある。

副作用として **ブラウザを開いていなくても製造が進む**（`/api/state` のたびに遅延評価）。
旧実装の「1tickあたり20個まで」の刻みも要らなくなった。

「止めている機械にはWPが入らない」「素材を変えてもWPはリセットしない」といったゲームの
ルールは旧実装のまま。売上（💰 / `sales_daily`）だけは**製品が完成した瞬間**に `tick()` が
積むように変えた（旧実装は🎁を開くまで加算されず、製造個数だけ伸びて売上が止まって見えた）。
回収（🎁を開く）の瞬間に行うのは図鑑登録と NEW 判定だけ。

### 3. 集計のキーはトークン。ペイロードの `user.email` は信用しない

OTLP のペイロードに入る `user.email` はクライアントの自己申告なので、そのまま集計キーに
すると誰でも他人になりすませる。トークンから引いた `user_id` をキーにし、食い違いは
`identity_mismatches` に記録するだけにしている。

### 4. マルチテナントの分離はテーブルの主キーで担保する

`agent_sessions` と `machines` の主キーは `(user_id, id)`。
`id` 単独にすると、他人と同じ session_id / レイアウトID を送るだけで相手の行を
書き換えられる（実装中に実際に踏んだ。`test/test_server.mjs` に回帰テストがある）。

### 5. ポーリングを削る

旧実装は `/api/sessions`（1.5秒）と `/api/otel`（3秒）の2本を叩いていた。実測すると
**ブラウザのポーリングはテレメトリ受信の30倍のリクエストを生む**（20人で 20 req/s 対 0.6 req/s）。
`/api/state` の1本にまとめたうえで、次の3つで削っている。

**(a) 変わらないものを送らない。** 実測（製造機11台・プロップ20個）でレスポンス 3,499B のうち
**2,351B が「ポーリング中には絶対に変わらない部分」**だった（配置・在庫・所持品・内装）。
`factories.rev` を持たせ、クライアントは `GET /api/state?rev=N` で自分の版を申告する。
一致していればサーバは `factory` を省略し、毎回変わる分（💰・各機械の `wp`/`running`・
エージェント・WP・今日の集計）だけを返す。
`rev` はミューテーション（購入・強化・配置・素材セット・稼働切替・回収）でだけ +1 する。

**(b) 間隔は10秒。** かつては「OTLP の logs バッチが5秒間隔だから5秒」としていたが、
**データの到着間隔ではなく、画面が見せている数字の時間軸に合わせるべき**だった。

製造の実測: 稼ぎは平均 34 WP/分・p90 71 WP/分（上限 200 WP/分）。2マス機は 4000 WP
なので埋まるまで 0.3〜2時間かかる。1回のポーリングで進む進捗バーは 0.07〜0.83% で、
幅200pxなら 0.1〜1.7px。**5秒と10秒の差は目で見えない。** 完成品の通知が最大10秒
遅れるが、2時間待った末の10秒なので実害がない。キャラの入退場も判定の閾値が
20秒〜5分（下の表）なのでもともと誤差。

代わりに Cloud Run の課金対象 CPU 時間がほぼ半分になる（`getState` はクエリ12本で
約390ms、無料枠は 18万 vCPU秒/月）。

**(c) 空振りの tick で書き込まない。** `tick()` は「前回から WP が増えたか」をロック無しの
SELECT で先に判定し、増えていなければトランザクションを張らずに返す。
以前は WP が1も増えていなくても `UPDATE factories SET last_tick_at` が走っていた。

実測（製造機11台・プロップ20個・エージェント4体、20人が同時にタブを開いた場合）:

| | リクエスト | 帯域 | 無駄な書き込み |
|---|---|---|---|
| 変更前（2秒・毎回一式） | 10 req/s | 34.2 KB/s | 10 writes/s |
| **変更後（5秒・差分）** | **4 req/s** | **4.6 KB/s** | **0** |
| | −60% | −87% | −100% |

（この計測は間隔が5秒だった当時のもの。その後10秒にしたので、リクエストはさらに半分になる）

1レスポンスは 3,946B（初回・一式）→ **1,179B（2回目以降）で −70%**。
加えて `document.visibilityState` が hidden の間はポーリング自体を止めている。

エージェントの状態反映は最大10秒遅れるが、実測で `UserPromptSubmit` は 2.5回/時・`Stop` は
2.3回/時しか発生しないので、遅延に気づく機会自体が少ない。

### 6. エージェントの在/不在は減衰で決める

`SessionEnd` は `kill -9` では飛ばないので、タイムアウトを併用する。しきい値は実データ
（38.4時間・207セッション・21,470区間）から決めた。

**「まだ居るか」は hook と OTel の新しいほうで測る。** hook は
`UserPromptSubmit`（開始）と `Stop`（終了）しか飛ばないので、その間に何分かかっても
`last_event_at` は動かない。hook だけで減衰させると、**90秒を超える作業は必ず
休憩に見える**（稼働中のエージェントが 💤 になる）。作業中は OTel が届き続けるので、
生存確認だけ `last_activity_at` で行う。OTel の粒度（中央値 9.6秒）は状態の
切り替えには使わないため、表示の遅延にはならない。

| ルール | 値 | 根拠 |
|---|---|---|
| busy → 休憩(☕)・hook基準 | 90秒 | OTel が一度も来ないセッションはこれだけで判定する |
| busy → 休憩(☕)・OTel基準 | 180秒 | 受信間隔は中央値 9.6秒 / p90 41秒。連続作業中の実測最大は 68.8秒（ログを出さない長いツール実行）。約2.6倍の余裕 |
| 退場（働いた実績あり） | 30分 | 30分超の沈黙は全区間の 0.05%。長い作業の最中に消さないよう、起点は hook と OTel の新しいほう |
| 退場（一度も働いていない） | 5分 | 207セッション中 191 が1分未満。長く残すと工場が残骸で埋まる |
| 入場 | busy は即時 / それ以外は20秒後 | 一瞬で終わるセッションでキャラをチカチカさせない |

OTel 基準を延ばすほど「`kill -9` で `Stop` が飛ばずに落ちたセッション」が 🟢 のまま
残る時間も延びる。180秒はそのトレードオフを踏まえた値。

コストは受信1回につき `UPDATE` 1発（イベント件数には比例しない）。実測で取り込みは
約8件/分だったので、追加負荷は無視できる。ブラウザ側は変更なし（ポーリングは10秒間隔）。

### 7. リーダーボードはグループ単位で見せる

リーダーボードに並ぶのは**自分と同じグループに居る人だけ**。どのグループにも入って
いない人には ☰メニューに項目自体を出さず、`GET /api/leaderboard` も 403 を返す
（画面の出し分けはクライアント側の判断なので、サーバでも断らないと URL 直打ちで漏れる）。

**`users.group_id` を1列足すのではなく `group_members` を挟んである。** いまの運用は
1人1グループだが、複数所属に広げる可能性があるため。`group_members(user_id)` の
UNIQUE 索引が「1人1グループ」を担保していて、複数所属を許すときは**この索引を1つ
落とすだけ**でよい（テーブルもクエリも作り直さなくて済む）。

そのため絞り込みは `JOIN` ではなく `EXISTS` で書いている。`JOIN group_members` にすると、
複数所属を許した将来に「2つのグループを共有している人」の行が2重になり `SUM` が倍になる。
**1人1グループのうちは同じ結果に見えるので、そのときには気づけない。**

```sql
AND EXISTS (SELECT 1 FROM group_members a
              JOIN group_members b ON b.group_id = a.group_id
             WHERE a.user_id = $3 AND b.user_id = u.id)
```

グループへの入り方は、いまは**アカウント作成時に既定グループへ自動追加**するだけ
（`DEFAULT_GROUP`、既定値 `bravesoft`）。★ 追加するのは**作成した「そのとき」だけ**で、
ログインのたびには入れ直さない。入れ直すと、グループから外した人が次のログインで戻って
しまい、あとで招待制にしたときに「外せないメンバー」ができる。
社外展開でグループ作成・招待を作ったら `DEFAULT_GROUP` を空にして自動追加を止める。

他人のデータを読むクエリは**リーダーボードのこの1本だけ**なので、絞り込みもここで完結する
（認証まわりの2本は自分の行を引いているだけ）。回帰テストは `test/test_server.mjs` の
`[7b] グループによる分離`。

## 既知の挙動（仕様として維持しているもの）

- **止めている機械にはWPが入らない。** 稼働させていない間に稼いだWPは繰り越されない。
  常時稼働のサーバでは「止め忘れると損する」度合いが上がる。
  変えるなら「工場全体のプールに溜めて、稼働中の機械が引く」形が候補。
- `?unlockall`（開発用の全解放）は **dev ログイン中は誰でも**効く。設定は要らない。
  SSO を設定した環境では閉じるが、`DEV_UNLOCK_EMAILS`（`.env` / Cloud Run の環境変数）に
  挙げた人だけは使える。未設定なら誰も使えない。使うとサーバログに記録が残る。
  リーダーボードが読むのは `scorecard_daily` と `wp_daily` だけなので、**順位には影響しない**。

  ```bash
  npm run dev            # 起動後 http://localhost:4321/?unlockall=1
  ```

  💰と在庫の正はサーバなので、クライアントだけで解放しても次のポーリングで消える。
  そのため実体は `POST /api/dev/unlockall`（ログイン中の**自分の工場だけ**を書き換える）。
  解放されるもの: 全背景・全床・全テーマシリーズ・製造機/プロップ/装飾の在庫を各3・💰999999。
  何度叩いても増殖しない（足すのではなく、その値まで底上げする）。

  ガードは `Auth.DEV_LOGIN`（＝`GOOGLE_CLIENT_ID` 未設定 かつ `DEV_LOGIN != 0`）を流用している。
  **SSO を設定した本番相当の環境ではルート自体が存在しない**（未知のルートと同じ 404）ので、
  デプロイ先で誰かが💰を無限に増やしてリーダーボードを壊す、ということは起きない。
  逆に言えば「SSO を設定しないまま共有サーバを立てる」と全員が使えてしまう点には注意。
