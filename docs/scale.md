# 規模を増やしたときどこが先に詰まるか（実測）

全社展開を検討したときに測った結果。**推測で優先順位を決めて2回間違えた**ので、
実測値と「何が何に比例するか」を残しておく。

測定日: 2026-08-20 / 環境: Cloud Run（東京・`max-instances 1`）+ Neon（シンガポール）

---

## 結論（優先順位）

| 順 | 項目 | いつ効くか |
|---|---|---|
| **1** | **`oauthStates` / `lastQs` をプロセス外へ** | **人数が増えた時点で即**。これが無いと `--max-instances 1` から出られない |
| 2 | 静的ファイルの再検証を減らす（`ASSET_MAX_AGE` を延ばす） | 人数 × リロード回数に比例。**リクエスト数の主因はこちら** |
| 3 | ポーリングのリクエスト数 | 30人あたりで無料枠の95% |
| 4 | `wp_daily` のマテリアライズ | **人数には比例しない**。1人の履歴が2年を超えるころ |
| — | 生ペイロードの保管 | PoC では不要と判断（2026-08）。保険の性質なので、必要になったら「その時点から」しか貯まらない点だけ承知しておく |

---

## 1. 何が何に比例するのか

ここを間違えると優先順位を誤る。**測ったら直感と違った。**

1人あたり20営業日ぶん（約3,480行）のデータを入れて、人数を増やして測った値。

| 人数 | `wp_source_minute` 総行数 | `totalWp`（1人） | リーダーボード（週） | マイページ（全期間） |
|---|---|---|---|---|
| 5 | 18,352 | 6ms | 3ms | 7ms |
| 20 | 70,552 | 6ms | 9ms | 7ms |
| 50 | 174,952 | **6ms** | 21ms | 7ms |
| 100 | 348,952 | **7ms** | 38ms | 7ms |

**`totalWp` は人数に対して平坦。** `WHERE user_id=?` で自分の行しか見ないため。
10秒ポーリングのたびに走る一番重い経路がこれなので、**人数はここに効かない**。

リーダーボードは人数に比例するが、100人でも 38ms で、しかも開いたときだけ走る。

### `totalWp` が重くなるのは「1人の履歴が伸びたとき」

同じクエリを、1人の行数だけ増やして測った値。

| 1人の行数 | 相当期間（174行/日） | `totalWp` |
|---|---|---|
| 2,000 | 半月 | 6ms |
| 20,000 | 約5ヶ月 | 69ms |
| 100,000 | 約2年 | 206ms |
| 400,000 | 約6年 | 757ms |
| 1,000,000 | 約16年 | 1,839ms |

実測の生成レートは **1人あたり 174行/日**（= 約3,800行/月）。
**着手の目安は 5万行（≒100ms）を超えたあたり**で、1人が毎日フルに使っても1年以上先。

> `wp_minute` / `wp_daily` をビューにしているのは「重みを UPDATE するだけで全期間が
> 再集計される」性質のため（[multiuser.md](multiuser.md) §1）。マテリアライズするときは
> `wp_weights` の変更時に作り直す経路を用意しないと、この性質が壊れる。

## 2. リクエスト数：主因は静的ファイルの再検証だった

無料枠は月200万リクエスト。

| 内訳 | 1人あたり月 | 前提 |
|---|---|---|
| ポーリング（`/api/state`） | **63,360** | 10秒間隔 = 360 req/時 × 8時間 × 22営業日 |
| **静的ファイルの再検証** | **126,500** | 1回のページロードで約1,150リクエスト（実測: うち1,111が304）× 5回/日 × 22日 |

**静的のほうが2倍多い。** `ASSET_MAX_AGE` が既定1時間なので、1時間空けてリロードするたび
1,150件の条件付きリクエスト（304）が飛ぶ。

`ASSET_MAX_AGE=604800`（7日）にすると **126,500 → 4,600 req/月/人**。絵を差し替えたときの
反映が最大7日遅れるトレードオフだが、リクエスト数への効き方は大きい。

ポーリングだけで見た人数の目安:

| 人数 | ポーリングのみ | 無料枠に対して |
|---|---|---|
| 10 | 633,600 | 32% |
| 20 | 1,267,200 | 63% |
| **30** | 1,900,800 | **95%** |
| 40 | 2,534,400 | 127%（超過） |

※ 稼働8時間×22営業日での計算。24時間で計算すると4倍になる（**この前提を書かずに
「20人で520万」と誤って見積もったことがある**）。

## 3. CPU 時間（インスタンス時間）

無料枠は月18万 vCPU秒。**レイテンシの単純合計で見積もってはいけない**（測り方は
[deploy.md](deploy.md#費用の測り方一度間違えたので手順を残す)）。

稼働88分・工場画面を1回開いた状態での実測:

| | 値 |
|---|---|
| レイテンシの単純合計 | 464秒 |
| **区間をマージした実時間** | **205秒**（2.3分の1） |
| 月換算 | 約10万秒 → 無料枠の 56% |

## 4. 人数が増えたとき最初に壊れるのは DB ではなくインスタンス数

`--max-instances 1` は必須の制約になっている。
`oauthStates`（[index.mjs](../server/index.mjs)）と `lastQs`（[ingest-otel.mjs](../server/ingest-otel.mjs)）を
プロセス内の Map で持っているため、2インスタンス以上にすると
**ログインが確率で失敗し、query_source が欠ける**。

つまり人数が増えても**インスタンスを増やせない**。1インスタンスに同時アクセスが集まると、
1件あたりの実処理が1ms未満でも待ち行列でレイテンシが膨らむ
（実測: 静的ファイルの304が189ms。[deploy.md](deploy.md) 参照）。

**全社展開の前提はここ。** 必要な変更は2つとも小さい。

- `oauthStates` → 署名付き Cookie か DB のテーブルへ
- `lastQs` → `agent_sessions` の列へ

## 測り方（再現手順）

**本番の共有DBにテストデータを入れないこと。** 下記はローカルの docker に対して実行する。

```bash
npm run db:up
```

```js
// 人数を増やしながら測る（1人 20営業日ぶん = 約3,480行）
// EXPLAIN (ANALYZE) の Execution Time を読む。往復(Neon まで約77ms)を含めないため
process.env.DATABASE_URL = "postgres://factory:factory@localhost:55432/factory";
const { all } = await import("./server/db.mjs");
const r = await all(`EXPLAIN (ANALYZE) SELECT COALESCE(SUM(wp),0) FROM wp_minute WHERE user_id=$1`, [id]);
```

生成したユーザーは `DELETE FROM users WHERE id=...` で消す（`ON DELETE CASCADE` で
関連行も落ちる）。
